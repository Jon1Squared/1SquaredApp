### End-to-end `row_version` optimistic concurrency (`ADR 0028 §6`, `R409`)

1. **Form & profile UI -> Server Action -> Repository (`R409`):**
   - `Matter` includes `rowVersion: number` (`>= 1`).
   - `src/components/MatterFormClient.tsx` (`:4072, 4177, 4441, 4570, 4653`) and `src/components/MatterProfileClient.tsx` (`:506`) store the loaded `matter.rowVersion` in state (refreshing it from `res.matter.rowVersion` after any inline save) and pass `expectedRowVersion` into `saveMatterAction(input, { id, saveMode, expectedRowVersion })` (`src/app/actions.ts:288`).
   - When `opts.id` is present (updating an existing matter), `saveMatterAction` and `saveMatterRecord` **require** a positive integer `expectedRowVersion` — rejecting a **missing** or **stale** `expectedRowVersion` with `CONFLICT_CONCURRENT_MODIFICATION` (`"This matter was updated by someone else. Reload the matter and try again."`), rendered as a clear conflict alert banner in `MatterFormClient` and `MatterProfileClient`.
2. **Every writer of `matters` checks `WHERE tenant_id = $1 AND id = $2 AND row_version = $3` and increments `row_version = row_version + 1` (`R409`):**
   - **Form / conversion save (1):** `saveMatterRecord` (`src/server/services.ts:3329`), including enquiry/quote conversion finalisation (`finalizeEnquiryConversionToMatter` `:8809`, `finalizeQuoteConversionToMatter` `:12333`).
   - **Targeted server-side matter mutations (7):** `markEngagementLetterDrafted` (`:4776`), `liftMatterRestriction` (`:4833`), `runMatterConflictSearchRecord` (`:4970` / `:5041`), `updateMatterConflictRecord` (`:5101`), `signOffMatterCostsRecord` (`:5367`), `reassignLeaverOwnedRecords` (`:1196` / `:1313`), and `executeMerge` (`:5639` / `:5799`) — each reads the current matter inside its transaction, updates via `WHERE tenant_id = $1 AND id = $2 AND row_version = $3` incrementing `row_version + 1`, and fails with `CONFLICT_CONCURRENT_MODIFICATION` if a concurrent transaction updated that matter row first.

### All-emails lookup for S0-30 (`B13`, `R410`) and staff/ethical-wall enforcement (`B12`)

- **`person_emails` synchronisation (`R410`):** every transaction that inserts, updates, imports, or merges a `Person` (`savePersonRecord` `:1446`, `createRecordFromPms` `:9452`, `executeMerge` `:5639` deactivating tombstoned `mergedId` rows, `importDirectoryAndMattersFromStore`, and `S0-17b` `employee_employment_records` saves for `firmWorkEmail`) replaces that person's `person_emails` rows in the **same transaction** from `person.emails` (`source = 'contact_email'`, preserving `active !== false` and `isPrimary`) plus `person.employment?.systems?.firmWorkEmail` (`source = 'firm_work_email'`, `active = true`).
- `findActivePeopleByEmail(ctx, emailLower)` joins `person_emails` (`active = TRUE`) to `people` (`merged_into_id IS NULL`) across **all** people (employees and non-employees alike), so `resolveOrProvisionEntraEmployee` (`:12469`) continues refusing any email shared by two people as ambiguous (`Entra ID Email Link Ambiguous`), and all S0-30 tests run unchanged.
- **Staff matters & ethical walls (`B12`):** every query returning matters or parties enforces `canAccessMatter` (`isStaffMatter` and `hasEthicalWall`, failing closed when `restrictedAccessUserIds` is empty) and redacts restricted conflict hits (`redactRecordId`).
