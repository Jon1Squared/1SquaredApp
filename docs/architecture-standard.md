# Platform Architecture Standard

Version 0.1 (draft) · 31 October 2026

## 1. Purpose and how to use this document

This standard defines how the Platform is structured, deployed and changed. It applies to every change, whether written by a person or generated by an AI coding tool. If a change cannot comply, record the exception as an architecture decision (section 14) before building it.

It protects three outcomes:

- The core stays one product, upgradeable for every client without rework.
- Each client’s configuration and bespoke work stays separate from the core and from other clients.
- No client can ever see another client’s data, in either hosting model.

## 2. Principles

1. **One core, many clients.** There is a single core codebase. Client differences are expressed as configuration or extensions, never as a fork or a client-specific branch of the core.
2. **Dependencies point one way.** Extensions and configuration depend on the core’s published interfaces. The core never imports, references or names a client.
3. **Same build, either hosting model.** The artefact deployed to a client’s Azure tenancy is identical to the one deployed to the hosted service. Only configuration and infrastructure differ.
4. **Isolation by default.** Tenant separation is enforced by the platform in layers, so one coding mistake cannot expose data.
5. **Configuration over code, extension over core change.** Use the least invasive mechanism that meets the need.
6. **Everything is versioned and reproducible.** Core, extension API, configuration schema and infrastructure are all versioned and deployed from source control.
7. **Secrets and data never live in code.**
8. **Least privilege, audited access**, including for our own staff.

## 3. The three layers

| Layer         | What it contains                                                                         | Who changes it                                 | Where it lives                                                                          | Versioning                                                |
|---------------|------------------------------------------------------------------------------------------|------------------------------------------------|-----------------------------------------------------------------------------------------|-----------------------------------------------------------|
| Core          | Product features, data model, extension API, configuration schema, security, tenancy     | Platform team only                             | Core repository                                                                         | Semantic versions, released to all clients                |
| Configuration | Per-client settings, branding, feature flags, custom fields, workflows, roles, templates | Platform team or trained client administrators | Stored as data, validated against the core schema; source copy in the client repository | Versioned, promoted through environments                  |
| Extensions    | Bespoke client-specific logic, integrations, screens, reports                            | Platform team                                  | Separate extension package per client                                                   | Own version, declares which core API versions it supports |

### Decision rule for any request

Ask in this order:

1. Can an existing configuration option achieve it? Configure it.
2. Would other clients plausibly want it? Build it into the core, behind a feature flag or a new configuration option.
3. Is it genuinely specific to one client? Build it as an extension using a published extension point.
4. Does it need something the core does not expose? Add a new, generic extension point to the core (reviewed as a core change), then build the extension on top. Never reach into core internals.

## 4. Repository and code structure

Core repository:

```text
core/
  src/
    domain/            business logic
    api/               public API and extension contract
    tenancy/           tenant resolution, tenant-scoped data access
    config-engine/     loads and validates tenant configuration
    extension-host/    discovers and runs extensions
  schemas/             configuration and extension manifest schemas
  infra/               infrastructure as code (Bicep)
  tests/
  docs/decisions/      architecture decision records
```

Client repository (one per client):

```text
client-<name>/
  config/
    base.json          tenant configuration
    environments/      dev, test, training, live overrides
  extensions/
    <extension-name>/
      manifest.json    name, version, supported core API range, permissions
      src/
  tests/
```

Rules:

- The core lives in one private repository. Each client has its own private repository for configuration and extensions. A shared repository with strict folder ownership is acceptable in the early stage, but it must be split before any client is given direct access.
- The core never contains client names, client IDs or client-specific conditions. A CI check fails the build if it finds one.
- Extensions may only import from the core’s public API package. A lint rule blocks imports from core internals.
- Each client repository pins a core version, upgraded deliberately and tested before release.

## 5. Configuration standard

- Configuration is defined by a schema owned by the core. Every option has a default, a type, a description and validation. Unknown keys are rejected.
- It is stored as data per tenant, not as code, so changes do not need a redeploy. A source-controlled copy in the client repository provides audit and promotion.
- Environments (dev, test, training, live) differ only through overlay files and environment variables.
- Changes are validated in CI against the current schema. Schema changes must be backward compatible within a major version: additive first, deprecate before removing.
- Typical scope: branding and theming, feature flags, custom fields, workflow steps, roles and permissions, document and prompt templates, integration endpoints (secrets by reference only).
- Every configuration change is audited: who, when, before and after.

## 6. Extension standard

- Extensions use named extension points: event hooks (before and after an action), UI slots, custom fields and validators, workflow steps, scheduled jobs, import, export and integration adapters, and report definitions.
- Each extension has a manifest stating its name, version, supported core API range, requested permissions and the extension points it uses.
- Extensions run through the extension host with only the permissions in their manifest. They receive a tenant-scoped context object: no raw database connection and no ability to name another tenant.
- The extension API is versioned separately and follows semantic versioning. A breaking change needs a major version, a deprecation period of at least two releases and migration notes.
- On startup and upgrade the host refuses to load an extension whose supported range does not match the core version.
- Every extension has automated tests, run in CI against the target core version.
- An extension failure must never take down the core. Each hook defines timeouts, error isolation and fail-safe behaviour.

## 7. Deployment models

| Aspect               | Model A: client-hosted (their Azure)                                                   | Model B: hosted by us                                          |
|----------------------|----------------------------------------------------------------------------------------|----------------------------------------------------------------|
| Tenancy              | Single tenant                                                                          | Multi-tenant                                                   |
| Infrastructure owner | Client’s Azure subscription                                                            | Our Azure subscription                                         |
| Identity             | Client’s Microsoft Entra ID                                                            | Per-tenant sign-in, ideally federated with the firm’s Entra ID |
| Data location        | Client’s tenant and chosen region                                                      | UK region (UK South, with UK West for recovery)                |
| Secrets and keys     | Client’s Key Vault                                                                     | Our Key Vault, separate secrets and keys per tenant            |
| Updates              | Versioned releases applied on an agreed schedule                                       | Rolled out through release rings                               |
| Support access       | Time-limited and client-approved (for example Azure Lighthouse or just-in-time access) | Break-glass, audited, one tenant at a time                     |
| Infrastructure code  | Same templates, deployed by the client or by us under agreement                        | Same templates, our subscription                               |

Rules:

- One build artefact (for example a container image) serves both models. Single-tenant versus multi-tenant is a configuration setting, never a separate codebase.
- All infrastructure is code, parameterised and stored in the core repository.
- A Model A installation must be repeatable by script, with a documented upgrade path and rollback.
- Model A client data never flows to our environments unless explicitly agreed. Any telemetry is opt-in and contains no client content.

## 8. Multi-tenant isolation standard (hosted model)

This section is mandatory for every change that touches the hosted model.

**Recommended isolation level:** because clients are law firms holding confidential data, use a database per tenant on shared compute. Compute is shared, which keeps cost down. Data is not shared. Azure elastic pools or per-tenant databases on a shared server keep the cost reasonable. A shared database with row-level security is acceptable only for low-sensitivity data, and only when the database itself enforces the policy.

Rules:

1. Tenant identity comes from the authenticated token, never from a URL, form field or header the user controls.
2. All data access goes through a tenant-scoped data layer. Queries that bypass it are forbidden and blocked in review and CI.
3. The tenant-scoped data layer connects to that tenant’s own database, or applies database-enforced row-level security. Application-level filters alone do not count as isolation.
4. Files and documents use a separate storage container per tenant, accessed with short-lived scoped tokens.
5. Each tenant has its own encryption keys in Key Vault. Customer-managed keys are offered to clients who ask.
6. Per-tenant secrets live in Key Vault, never in configuration files, logs or the repository.
7. Caches, queues, search indexes and background jobs carry the tenant ID in every key, message and job context. Jobs refuse to run without it.
8. Logs and telemetry are tagged with the tenant ID and contain no client content or personal data. Support staff can view only one tenant at a time.
9. Each tenant can be backed up and restored independently, tested at least quarterly. Restoring one tenant must never touch another.
10. Offboarding has a documented process: export, then permanent deletion of the tenant’s data, keys and storage, with confirmation.
11. Extensions run only in their own tenant’s context and cannot read another tenant’s configuration.
12. Per-tenant rate limits and resource quotas protect against noisy neighbours.

Isolation tests (a release gate):

- Automated tests create two tenants, populate both, and prove that every API endpoint, report, export, search, file download and background job returns only the calling tenant’s data. A failure blocks release.
- Tests also try tampered identifiers: another tenant’s record IDs and forged tenant claims.
- An independent penetration test is carried out before the first hosted client goes live, and annually after that.

## 9. Identity, access and administration

- Authentication uses OpenID Connect, with Microsoft Entra ID supported in both models. Multi-factor authentication is required for all administrative roles.
- Role-based access control is defined in the core. Clients map their own roles through configuration.
- Platform staff access to production uses separate accounts, is time-limited, approved and logged. There is no standing access to client data.
- Service-to-service access uses managed identities, not shared passwords.

## 10. Data protection and compliance

- Treat all client data as confidential legal data and as personal data under UK GDPR. In the hosted model we act as processor, with written data processing terms for each client.
- Hosted data stays in UK regions unless a client agrees otherwise in writing.
- Encryption in transit (TLS 1.2 or later) and at rest, everywhere.
- Retention and deletion rules are configurable per tenant within defined limits.
- An immutable audit log records sign-ins, configuration changes, extension changes and data exports.
- Work towards recognised assurance such as Cyber Essentials Plus and ISO 27001, because law firm clients will ask for it in due diligence.
- If the Platform includes AI features: document which data goes to which model provider for each tenant, ensure no client content is used for training, and make the provider choice configurable per tenant.
- This is a technical standard, not legal advice. Have contract and data protection terms reviewed by a solicitor.

## 11. Environments and release management

- Environments are dev, test, training and live. Each has its own database, secrets and URL. Live data is never copied down without anonymisation.
- Branches run feature branch to develop to main. Main is protected and every change needs a reviewed pull request.
- Core releases use semantic versions (MAJOR.MINOR.PATCH) with tags and release notes. The training environment is built from release tags.
- In the hosted model, releases roll out in rings: an internal tenant, then a pilot client, then all clients. Model A clients upgrade on their own schedule within a supported window, for example within two minor versions of the latest release.
- Database migrations are backward compatible (expand, then contract) so any release can be rolled back. They are run and tracked per tenant.
- Every release has a tested rollback plan. Configuration and extensions deploy independently of the core where possible.
- Hotfixes branch from main, are tested and released, then merged back to develop.

## 12. Testing standard

| Test type                   | Scope                                                                                | Gate                                                       |
|-----------------------------|--------------------------------------------------------------------------------------|------------------------------------------------------------|
| Unit                        | Core logic                                                                           | Every pull request                                         |
| Contract                    | Extension API and configuration schema, against sample extensions and configurations | Every pull request                                         |
| Tenant isolation            | The two-tenant tests in section 8                                                    | Every pull request touching data access, and every release |
| Extension and configuration | Each client’s extensions and configuration against the target core version           | Before upgrading that client                               |
| End to end                  | Key user journeys in the test environment                                            | Every release                                              |
| Security                    | Dependency scanning, secret scanning, static analysis                                | Every pull request                                         |

## 13. Observability, cost and support

- Structured logs carry a correlation ID and tenant ID, and never client content.
- Per-tenant dashboards show errors, performance, usage and storage.
- Azure cost tags per tenant track margin, with billing alerts on every subscription.
- Maintain runbooks for onboarding a tenant, upgrading a client-hosted installation, restoring a tenant, offboarding a tenant and incident response.

## 14. Change control: the standard every change must meet

### Classify the change

| Class                | Examples                      | Extra requirements                                                            |
|----------------------|-------------------------------|-------------------------------------------------------------------------------|
| Core feature         | New module, data model change | Decision record if structural, documentation, isolation tests, migration plan |
| Core extension point | New hook or API               | Versioned API change, contract tests, deprecation plan if breaking            |
| Configuration option | New setting or flag           | Schema entry, default, validation, documentation                              |
| Client extension     | Bespoke screen or integration | Manifest, permissions review, tests, lives in the client repository           |
| Client configuration | Branding, workflow tweak      | Validated against schema, promoted through environments                       |
| Infrastructure       | New Azure resource            | Infrastructure as code only, cost estimate, security review                   |

### Definition of done

Every pull request must confirm:

- [ ] Classified correctly, and no client-specific logic is in the core.
- [ ] Dependencies point one way (extensions to core API).
- [ ] Works in both hosting models (single-tenant and multi-tenant).
- [ ] All data access is tenant-scoped and isolation tests pass.
- [ ] No secrets, client names or client data in code, logs or test fixtures.
- [ ] Configuration changes have schema, default and validation, and are backward compatible.
- [ ] Extension API changes are versioned, contract-tested and deprecation-noted.
- [ ] Migrations are backward compatible and reversible.
- [ ] Tests added and CI passes, including security scans.
- [ ] Documentation and release notes updated.
- [ ] Help & documentation updated.
- [ ] Cost and performance impact considered.
- [ ] Any exception to this standard is recorded as a decision record and approved.

### Architecture decision records

Any structural decision, or exception to this standard, gets a short note in docs/decisions/ covering context, decision, alternatives considered, consequences, date and status.

## 15. Using this standard with AI coding tools

Put the summary below in the project’s rules file (CLAUDE.md for Claude Code, and the equivalent rules or instructions file in Antigravity) so every generated change follows it. Ask the reviewing tool to check each pull request against section 14.

```text
Architecture rules for this project (see Platform Architecture Standard):

1. Never put client-specific code, names or IDs in the core.
2. Client differences are configuration (schema-validated) or extensions (public extension points only).
3. Extensions import only from the public API package, never core internals.
4. All data access goes through the tenant-scoped data layer. The tenant comes only from the authenticated token.
5. No secrets, keys or client data in code, logs, tests or config files.
6. The same build must run single-tenant (client Azure) and multi-tenant (hosted).
7. Configuration and extension API changes must be backward compatible within a major version.
8. Database migrations must be backward compatible and tracked per tenant.
9. Any change touching data access needs two-tenant isolation tests.
10. If a request conflicts with these rules, stop and explain before coding.
11. Every change must create or update the relevant pages in the application's Help & documentation section, in the same pull request.
```
