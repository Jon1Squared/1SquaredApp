# 1Squared — Release Notes

## Unreleased — External Document Store Integration (Phase 1: SharePoint Online)

### Change Classification (Platform Architecture Standard Section 14)

- **Core Feature (`@platform/core`):**
  - Provider-agnostic `DocumentStoreProvider` abstraction (`core/src/domain/documents/` and `core/src/integrations/document-stores/`).
  - SharePoint Online provider (`SharePointDocumentStoreProvider`) using Microsoft Graph v1.0 for folder/file operations and SharePoint REST (`breakroleinheritance` / `resetroleinheritance`) for folder permission inheritance management.
  - Two-identity security model:
    - `user` access context: On-Behalf-Of (OBO) delegated Graph token exchange so SharePoint enforces each user's own permissions and records their identity in its audit trail.
    - `provisioning` access context: Application-only certificate authentication (`Sites.Selected` `fullcontrol` on the target site only) restricted to background jobs and admin connection/location/permission operations.
  - Per-tenant, per-user AES-256-GCM encrypted OBO token cache (`EncryptedUserTokenCache`) keyed by `${tenantId}:${entraObjectId}`.
  - Inheritance-based security model (`{departmentCode}/{teamCode}/{matterFolderName}`) mapped to Microsoft Entra ID security groups, with restricted-matter inheritance breaking and closed-matter read-only locking.
  - Matter folder template engine supporting three-tier inheritance (`workType → department → default`) with `extends` (deep merge by path) and `replace` modes.
  - Matter lifecycle background jobs (`provisionMatterDocumentsJob`, `reconcileMatterPermissionsOnTeamChangeJob`, `applyMatterRestrictionDocumentsJob`, `applyMatterClosureDocumentsJob`, `linkExistingMatterFolderJob`) and permission drift reconciliation (`reconcileTenantDocumentPermissionsJob`).
  - 7 new RBAC permissions registered in `PERMISSION_REGISTRY`: `document:download`, `document:upload`, `document:edit`, `document:provision`, `document_store:configure`, `document_template:configure`, and `document_access:review`.
  - Admin UI (**Administration › Document Stores & DMS**: Document stores, Routing & access, Folder templates, Access review) and Matter UI (**Matter › Documents**: SharePoint Document Store browser, breadcrumb navigation, drag-and-drop upload, effective-access gating, deep links to SharePoint & Desktop Office apps, and link-existing-folder workflow).
- **Core Extension Point (`@platform/core/api`):**
  - Exported `DocumentStoreProvider`, `UserAccessContext`, `ProvisioningAccessContext`, `DocumentStoreCapabilities`, `GroupMembershipSync` (Phase 2 interface), and lifecycle hooks `afterMatterDocumentsProvisioned` and `beforeMatterDocumentsClose`. Additive minor extension API update (`1.1.0`).
- **Configuration Options (`core/schemas/tenant-config.schema.json`):**
  - Added optional `documentStores`, `documentRouting`, `matterFolderNameTemplate`, `documentAccess`, and `matterFolderTemplates` sections to `TenantConfigSchema`, plus cross-entity validation (`validateDocumentConfigAgainstTenantData`).
- **Client Configuration (`client-not-a-law-firm/config/base.json`):**
  - Configured the demo tenant's SharePoint store (`1squared1.sharepoint.com`, `/sites/NotALawFirm`, `Not A Law Firm Document Repository`), routing rules, 11 department + 16 team Entra security group mappings, and default + Conveyancing + Litigation folder templates.

### Hosting Model Compatibility (Model A `single_tenant` & Model B `multi_tenant`)
- The identical build runs in both `single_tenant` (Model A, client-hosted Azure with Managed Identity or client App Registration) and `multi_tenant` (Model B, 1Squared-hosted with per-tenant App Registration or multi-tenant App Registration with admin consent).
- Zero document content, file bytes, or SharePoint item listings are cached or persisted in 1Squared databases or storage.

### Database Migrations & Rollback (`0002_document_store_integration_expand`)
- **Expand Migration (`0002_document_store_integration_expand`):**
  - Creates tenant-scoped tables `matter_document_locations` (with Row-Level Security `rls_matter_document_locations_tenant`) and `document_reconciliation_findings` (with RLS `rls_document_reconciliation_findings_tenant`).
  - Adds nullable `entra_object_id`, `restricted_access`, and `folder_template_id` columns.
- **Rollback (`downSql`):**
  - Drops RLS policies and tables `document_reconciliation_findings` and `matter_document_locations`, and drops the additive columns safely. Because `0003` and `0004` do not list `0002` in `dependsOn`, `rollbackVersion(ctx, '0002')` runs as a standalone step without rolling back `0003` or `0004`, leaving key-date tables intact.

## Security, Tenancy & Architecture Standard Remediation (`feat/platform-architecture-standard`)

### Breaking & Operational Changes
- **Demo Mode (`featureFlags.enableDemoMode`):**
  - `featureFlags.enableDemoMode` defaults to `false` in `base.json` and environment overlays (`config/environments/dev.json`), and must be explicitly enabled in a non-live tenant configuration.
  - Schema and runtime validation reject `featureFlags.enableDemoMode: true` whenever `environment === 'live'`.
  - Demo Mode persona switching requires `isDemoModeEnabled() === true` (`featureFlags.enableDemoMode === true`, `environment !== 'live'`, and `NODE_ENV !== 'production'`; `homePagesConfig.firmSettings.demoMode` is derived from `isDemoModeEnabled()` and is not a separate setting), requires a target persona marked `demo: true`, and verifies that the signed-in actor holds every permission of the target persona and can access every restricted/staff matter (`restrictedAccessUserIds`) accessible to the target persona.
- **Tenant Package Resolution, Server-Only Boundary & Dynamic Extension Registration (`PLATFORM_TENANT_PACKAGE_DIR`):**
  - `src/platform/tenantRuntime.ts` and `src/server/rbacRuntime.ts` are guarded with `import 'server-only'`, and domain modules (`src/domain/homeConfig.ts`, `src/domain/matterCosts.ts`, `src/domain/documentGeneration.ts`, `src/domain/rbac.ts`, `src/domain/employment.ts`) no longer statically import `tenantRuntime.ts` or read tenant configuration in browser contexts.
  - `PLATFORM_TENANT_PACKAGE_DIR` must be explicitly configured outside `NODE_ENV === 'test'`; `resolveTenantPackageDir()` throws `TENANT_CONFIG_ERROR` when unset rather than falling back to the first `client-*` directory.
  - At build time, `scripts/generate-extension-registry.ts` writes an empty registry (`[]`) with zero client imports when `PLATFORM_TENANT_PACKAGE_DIR` is unset (unless `--all-fixtures` is passed for the test suite), merges `config/base.json` and the active environment overlay through `loadAndValidateTenantConfig`, validates each enabled extension's `manifest.json`, rejects duplicate extension IDs (`DUPLICATE_EXTENSION_ID`), and generates the git-ignored `src/platform/generated/extensionRegistry.ts` so `src/platform/tenantRuntime.ts` contains zero client-specific paths.
  - `getPlatformExtensionHost()` validates each `manifest.json` against `ExtensionManifestSchema`, checks compatibility with the extension module's exported `manifest`, registers only extensions listed in `tenantConfig.enabledExtensions`, isolates and logs load failures (`extension_load_failed` / `EXTENSION_MANIFEST_ERROR`) with unique correlation IDs (`ext-load-${randomUUID()}`), and caches the `ExtensionHost` instance.
  - `saveMatterRecord` is `async`, requires a verified Entra session (`activeActorSession?.verifiedSession`) to construct `TenantContext` via `resolveCurrentTenantContext(createVerifiedSessionActorFromEntraSession(...))` at the start of the call (returning `UNAUTHENTICATED` when missing), awaits `host.executeMatterCostsHook('beforeMatterCostsCalculate', ...)` and `host.executeMatterCostsHook('beforeMatterOpen', ...)`, and blocks matter opening (`errors.costsGovernance`, `matter: null`) whenever an enabled `beforeMatterOpen` hook returns `allowProceed: false`, throws an error, times out (`hookTimeoutMs`, default `2,000 ms`), or fails to load (note: a CPU-bound synchronous hook invoked via `executeMatterCostsHookSync` cannot be interrupted mid-execution by a timer). Monotonic ID counters are never rolled back on a veto, and `saveMatterRecord` verifies that the stored matter's `updatedAt` has not changed while awaiting hooks (`errors.conflict`) before committing inline-created people, organisations, enquiry links, or matter updates.
- **Infrastructure (`core/infra/main.bicep`):**
  - `entraClientId` and `entraRedirectUri` are now required Bicep parameters (no empty-string defaults), `vnetAddressPrefix` and `appServiceSubnetPrefix` are parameterised for hub-and-spoke environments, and Key Vault network ACLs are configured so Azure App Service can resolve `@Microsoft.KeyVault(...)` secret references at runtime.
- **Scoped Blob Download Token Signing (`PLATFORM_BLOB_SIGNING_KEY`):**
  - `PLATFORM_BLOB_SIGNING_KEY` must be configured in Key Vault / environment in non-test environments (`resolveTenantBlobSigningKey`). The legacy static fallback key has been removed, and signature verification uses constant-time `crypto.timingSafeEqual`.
- **Transitional Local Store (`data/runtime-store.json`):**
  - Local runtime state writes to the git-ignored `data/runtime-store.json` (bootstrapped from the tracked seed snapshot `data/seed-not-a-law-firm.json`), preventing dirty working trees during development and testing.
  - All invented employee and client fixture email addresses now use RFC 2606 reserved domains (`notalawfirm.example`, `*.example`, `example.com`) and Ofcom drama telephone ranges.
- **Entra ID Session & RBAC Isolation:**
  - `TenantContext` requires a branded `VerifiedSessionActorInput` minted exclusively from a cryptographically verified `VerifiedEntraSessionPayload` in `src/server/entraAuth.ts` (never overriding `session.tenantId`), and `resolveCurrentTenantContext` rejects actors missing `email` or `entraObjectId` or whose `actor.tenantId` does not match `cfg.tenantId` (`TENANCY_FORGERY_DETECTED`).
  - In `hybrid` authority mode, token-derived roles are resolved strictly from the active `runWithActiveActorSession` (`AsyncLocalStorage`) request scope for that exact `(tenantId, personId)` (using the verified session's expiry), with no server-wide mutable session map.
  - Added `matter:create`, `matter:edit`, `matter:reassign_ownership`, `matter:restriction:lift`, and `matter:costs:sign_off` RBAC permissions (`matter:reassign_ownership` is granted to `supervisor`, `partner`, `managing_partner`, and `admin`, and not to `is_team_lead_of_any_team`; `matter:restriction:lift` is granted to `managing_partner`, `risk_compliance`, and `admin` with `requiresMfa: true`; `matter:costs:sign_off` is granted to `partner`, `managing_partner`, and `admin`) enforced in `saveMatterRecord`, `signOffMatterCostsRecord`, `updateMatterConflictRecord` (which requires `matter:edit`, plus `risk:view` when setting conflict status to `Approved` or `Declined`, builds `ConflictCheckRecord` on the server via `buildServerConflictCheckRecord` in both `saveMatterRecord` and `updateMatterConflictRecord`, preserves existing conflict comments and runs verbatim, stamps server-side author/approver IDs and timestamps, records `approvedRestrictedMatchIds` on `Approved`, and only transitions a referred matter to `Active` when `matterOpeningGate.allowProceed === true`), and `liftMatterRestriction`, plus server-side validation of `owningDepartmentId` and `owningTeamId` against active `store.orgStructure` records on create or when changed.
  - `saveMatterRecord` strips server-owned governance keys (`partnerCostSignOffCompleted`, `partnerCostSignOff`, `matterOpeningSnapshot`, `matterOpeningGate`, `matterCostsGovernance`, `riskAssessment`) from `input.fieldValues`, ignores caller-supplied `conflictClearedById`, determines whether an existing matter has already opened from status alone (`existingHasOpened = Boolean(existing && existing.matterStatusId !== prospectiveStatus && !existing.matterNumber.startsWith('DRAFT'))`) and whether a save opens a matter from the resulting status (`willOpen = !existingHasOpened && nextStatusId !== prospectiveStatus`), backfills a `matterOpeningSnapshot` (`saveMode: 'backfilled'`, `capturedAt: now`, `captureNote: 'Recorded after opening: matter opened before opening snapshots were captured.'`, displayed as **Recorded after opening**) on the next save of an already-opened matter that lacked a snapshot without re-running the opening gate, maps legacy `conflictCheckStatus` values fail-closed via `conflictStatusPillFromLegacy` / `conflictOutcomeLabelFromLegacy` (`'Potential conflict — escalated'` and unknown statuses map to `'Referred'`; `resolveMatterConflictCheckRecord` records `approvedById` / `approvedByName` / `approvedAtDisplay` only when status is `'Cleared'` or `'Approved'` and `conflictClearedById` is present), refuses any attempt by a caller without `risk:view` to clear a matter whose conflict check is `'Referred'` (`errors.conflict: "This matter has been referred to Risk. Only Risk & Compliance can clear or approve it."`), requires a `Cleared` (with no unapproved restricted matches) or Risk-`Approved` conflict check before `willOpen` can proceed (`errors.conflict`), runs the unified `runMatterOpeningGate` helper (checking `getExtensionHostLoadErrors()` for enabled `beforeMatterOpen` extensions and reporting load failures under `errors.extensions`, `evaluateMatterKeyDateOpeningGate` for required key dates when the Key Dates module is enabled, and `beforeMatterOpen` extension hooks; brand-new matters with `requiredKeyDateTypeIds` must be saved as a draft first so required key dates or Not-applicable reasons can be recorded before they can be cleared or referred), blocks the save when `willOpen` or `saveMode === 'submit_referred'` and `!gateResult.allowProceed` while allowing ordinary edits on Prospective matters (such as stage changes) to refresh `matterOpeningGate` non-blockingly, sets `matterOpeningGate.allowProceed = false` on draft saves of unopened matters so only a real `runMatterOpeningGate` execution can write `allowProceed: true`, skips the interactive conflict-decision rule and opening gate on server-only PMS imports (`opts.source === 'pms_import'`, writing a `matter-imported-open` audit entry, while `saveMatterAction` forwards only `{ id, saveMode, byId }` and `saveEnquiryAction` forwards only `{ id, asDraft, byId }`), preserves `matterOpeningSnapshot` once a matter has opened, and resets `partnerCostSignOffCompleted` / `partnerCostSignOff` when the matter's fee estimate (`resolveMatterSignOffEstimateGbp`: fee estimate, agreed cap, or calculated estimate) differs from the amount signed off. Partner cost sign-off is set exclusively via `signOffMatterCostsRecord` (`signOffMatterCostsAction`), which enforces `matter:costs:sign_off`, runs `runMatterOpeningGate`, and writes an audit entry. Both `updateMatterConflictRecord` and `signOffMatterCostsRecord` only activate a referred matter when `matter.matterStatusId === prospectiveStatusId`, `matterOpeningGate.allowProceed === true`, and `evaluateMatterKeyDateOpeningGate` pass.
  - All server snapshots and list/detail endpoints (`getAppSnapshot`, matter-linked tasks, links, enquiries, quotes, notes, audit entries, PMS matter/client/admin views, and key-date diaries/exceptions) and matter conflict searches (`runMatterConflictSearchRecord`, `saveMatterRecord`, and `updateMatterConflictRecord`) use the shared `buildRecordVisibility` helper (`src/server/visibility.ts`) so restricted (`isStaffMatter`) and ethical-wall (`hasEthicalWall`) matters and restricted enquiries (personal `Draft` enquiries belonging to another user or enquiries converted into/linked to a hidden matter) are never exposed to unauthorised users. Conflict searches run exclusively server-side (with no browser fallback in `MatterFormClient.tsx`), return redacted matches (`Match on a restricted matter` / `Match on a restricted enquiry`, `restricted: true`, preserved through `reconcileServerConflictMatches`) when a match falls on a matter or enquiry the caller cannot view, log a count-only `conflict_search_restricted_match` structured log (and write a matter audit entry when `currentMatterId` is a saved matter, with zero party or matter names), and refuse `submit_cleared` whenever any restricted match ID is not in the server-recorded `conflictCheckRecord.approvedRestrictedMatchIds` (`hasUnapprovedRestrictedMatches`, including for `risk:view` holders unless `status: 'Approved'` is recorded). Only `matter:restricted:access` shows Risk & Compliance reviewers the full match on a restricted matter, and other users' personal `Draft` enquiries always show as restricted.
  - Every in-place matter write outside `saveMatterRecord` stamps `updatedAt` and `updatedById` (`touchMatter`), and `saveMatterRecord` re-evaluates `hasEmployeeParticipant` against the latest `store.people` after awaiting extension hooks so concurrent hires or matter edits are detected.
  - `src/domain/rbac.ts` requires explicit `config.rbac` and `tenantId` parameters (with no module-level RBAC config cache or `'default'` tenant fallback), supplied on the server via `src/server/rbacRuntime.ts` (which throws `TENANT_MISMATCH` if called for a tenant other than the active tenant) and passed to client components via `getAppSnapshot().rbacConfig`.
  - Clearing `isStaffMatter` or `hasEthicalWall` on an existing matter is ignored by `saveMatterRecord` and requires the dedicated `liftMatterRestriction` service/action (`matter:restriction:lift`, `mfaVerified === true`, and a mandatory audit reason writing a `matter-restriction-lift` audit entry). Lifted state is persisted in `matter.restrictionLift` across subsequent saves (tracking working employees via `isWorkingAtFirm`) and is only reinstated if a new employee participant or a new `information_barrier` match ID is added.
  - Referred conflict review task routing and `getAppSnapshot` governance suggestions share `src/server/conflictReview.ts` (`resolveConflictReviewTeam`, `resolveSuggestedConflictReviewer`, `resolveConflictReviewTaskRouting`) using the tenant configuration option `conflictReview` (`assigneeTeamKey`, `assigneeRoleKey`) matching `assigneeTeamKey` strictly by team `id` or organisation team `id`/`code` (never display names), filtering candidate assignees by `canPersonAccessMatter`, leaving the task unassigned in the team queue (logging `conflict_review_task_unassigned`) when no permitted assignee matches, and omitting client/matter names from the task title and description on restricted matters when unassigned.
  - Deprecated `branding.contactEmail` and `branding.website` in favour of `firm.contactEmail` and `firm.website` (keeping `branding.*` backward-compatible with deprecation warnings while enforcing email and hostname/URL format validation on `firm.contactEmail` and `firm.website`).
  - `getEmployeeDetailsForUser` returns `sensitive: null` unless `logViewSensitive: true` is passed and `logEmployeeRestrictedAccess` records a `view-sensitive` audit entry.
- **Key Dates & Limitation Governance:**
  - Limitation date calculations are verified server-side against the `(ruleSetId, ruleId)` pair in tenant configuration, and `keydate:override_calculation` is enforced in `src/domain/keyDates.ts` (`createOrProposeKeyDate` lines 771–783 and `supersedeConfirmedKeyDate` lines 1268–1283) as well as in `assembleKeyDateCalculation` (`buildKeyDateCalculation` and `previewKeyDateCalculation`) in `src/domain/keyDateCalculator.ts`.
  - Superseding a confirmed calculated key date to a different due date (or after its limitation rule set has been retired from configuration) requires `keydate:override_calculation` and a recorded override reason, writing a `keydate-override-calculation` audit entry.
  - Reminder task idempotency keys are tenant-scoped (`keydate-reminder:${tenantId}:${keyDateId}`), restricted/staff matters with no permitted assignees surface a distinct `restricted_matter_no_permitted_assignee` compliance exception without leaking task details, and orphan key dates referencing a missing matter surface an admin-only (`keydate:configure`) `orphan_key_date_missing_matter` exception with `keyDateId` only.
  - Added reversible per-tenant migration `0004` (`version: '0004'`, `name: '0004_key_date_reminder_last_skipped_reason_expand'`, `dependsOn: ['0003']`, adding `last_skipped_reason` on `key_date_reminder_states`), with `TenantMigrationRunner` enforcing `dependsOn` prerequisites on `applyUp` (`MIGRATION_DEPENDENCY_ERROR`) and refusing `rollbackVersion` only when an applied migration lists the target in `dependsOn` (`MIGRATION_ROLLBACK_ORDER_ERROR`).
  - Phase 1 Calendar Sync is read-only / disabled pending Phase 2 Microsoft Graph calendar integration.
